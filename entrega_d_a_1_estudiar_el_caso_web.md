| :-: | :--- | :--- | :--- | :--- |
| **1** | **Trámites en archivos sueltos y código repetido:** Cada página (alta, cobro, seguimiento) duplica la revisión de sesión, bitácora y encabezados. Si cambia el token, hay que editar 40 archivos. | Ya incluye el enrutador central en `urls.py` (*Front Controller*) y la pila de `MIDDLEWARE` en `settings.py` para autenticación, sesiones y seguridad global. | Configurar las rutas en `urls.py`, crear las vistas delgadas (`views.py`) y, si ocupamos algo propio, programar un middleware personalizado. | No tenemos que armar un *Front Controller* a mano con Servlets ni programar una cadena de responsabilidad (*Chain of Responsibility*) manual con clases base y punteros. |

Django es un framework web de infraestructura, no resuelve la lógica de negocio ni la logística de envíos. | Modelar el contrato del medio con clases/funciones por transporte (*Strategy*), crear un traductor (*Adapter*) para homologar lo que diga la IA a `Sugerencia(medio, motivo)`, y una fábrica simple para instanciar el medio. | No vamos a meter un *Factory Method* complejo con familias de clases abstractas si con una fábrica simple alcanza, ni patrones pesados como *Bridge* o *Visitor*. |

La plantilla solo debe pintar. | No vamos a usar esquemas de transformación raros tipo *Transform View* (XML/XSLT) ni armar el HTML a mano con código. |
| **4** | **Falta de consistencia y cobros dobles:** Si falla el correo de confirmación, se cae el alta del envío. Además, si el cliente presiona dos veces "Pagar", se cobran dos pedidos. | La función `transaction.atomic()` para transacciones de base de datos (*Unit of Work* implícito) y utilidades de redirección HTTP (`redirect()`). | Envolver el cobro y alta en `with transaction.atomic():`, disparar los avisos/correos solo tras confirmar el guardado (`on_commit`), y aplicar el flujo Post-Redirect-Get (PRG) e idempotencia para evitar cobros dobles. | No tenemos que programar un *Unit of Work* manual en memoria que rastree listas de objetos modificados, ni un bus de eventos enterprise complejo. |
| **5** | **Clientes web y móvil con requerimientos distintos:** La app móvil necesita un JSON ligero (`folio, estado, eta`) y hoy hace 12 peticiones para pintar el inicio, mientras el panel web necesita HTML con mapa. | Vistas flexibles que pueden retornar tanto plantillas HTML como respuestas JSON nativas con `JsonResponse`. | Crear un endpoint de agregación (`GET /api/pedidos/<id>`) para que la app móvil obtenga todo en una sola petición, consumiendo la misma capa de servicio (`PedidoService`) del panel web. | No vamos a montar dos backends separados ni crear un servidor BFF (Backend For Frontend) externo en otro lenguaje solo para darle formato al JSON. |
| **6** | **Caídas de servicios externos que congelan el sistema:** El mapa y la IA fallan frecuentemente; mientras no responden, el usuario se queda con la "rueda infinita" y no puede consultar pedidos que ya están guardados localmente. | Django no trae mecanismos de tolerancia a fallos ni Circuit Breaker por defecto en su núcleo básico. | Desacoplar las llamadas externas de las consultas locales: configurar tiempos de espera (*timeouts*), manejo de excepciones y degradación elegante (si la IA o el mapa caen, mostrar el pedido guardado con un aviso). | No vamos a montar arquitecturas sobrediseñadas de microservicios ni mallas de servicios (*Service Mesh*); basta con control defensivo de errores y timeouts en la integración. |
| **7** | **Propuesta de sobreingeniería para un simple PDF:** Un proveedor propone meter Event Sourcing, CQRS y Redux global solo para autenticar, consultar un pedido y generar una guía en PDF. | Vistas estándar, autenticación nativa lista y soporte para servir archivos mediante respuestas HTTP (`FileResponse` / `HttpResponse`). | Una vista simple y protegida que consulte el pedido existente y retorne el archivo generado. **Saber decir que no** a la sobreingeniería innecesaria. | Rechazar completamente Event Sourcing, CQRS y Redux (evitar el *Golden Hammer* / YAGNI); no meter patrones complejos cuando el problema es un trámite básico de consulta y descarga. |

## 2. Al final del día: Conclusiones arquitectónicas

1. **¿`urls.py` es Front Controller, Page Controller, o el camino hacia los dos?**  
   **`urls.py` no es ni uno ni otro por sí solo, sino el camino (el mapa) que los conecta.**  
   El verdadero *Front Controller* es el propio motor interno de Django (su manejador de peticiones), que recibe cualquier solicitud HTTP que entra al servidor. Ese manejador consulta `urls.py` como si fuera un directorio de rutas para saber a dónde mandarla, y termina delegando la lógica al *Page Controller*, que son las funciones o clases que nosotros programamos en `views.py`.

2. **¿La plantilla Jinja/Django puede hacer `SELECT`? ¿Por qué sí o por qué no?**  
   **Técnicamente sí puede, pero por buenas prácticas no debería.**  
   - **Por qué sí puede:** Porque el ORM de Django funciona con carga perezosa (*lazy loading*). Si en el HTML escribimos algo como `{{ pedido.items.all }}` o llamamos a una relación como `{{ pedido.cliente.nombre }}` que la vista no consultó antes, Django va a hacer la consulta a la base de datos en ese preciso instante al pintar la pantalla.  
   - **Por qué no debe:** Porque rompe la idea de una plantilla (*Template View*). La plantilla solo debe preocuparse por cómo se ve la información que ya le pasó la vista en el `context`. Si permitimos que el HTML haga consultas por su cuenta, podemos provocar problemas de lentitud o sobrecargar la base de datos (el famoso problema de consultas $N+1$) sin darnos cuenta.
